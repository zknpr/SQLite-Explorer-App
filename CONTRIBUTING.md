# Contributing to SQLite Explorer

The desktop application has two source repositories:

| Change | Source |
| --- | --- |
| Native menus, dialogs, file access, lifecycle and IPC | `src-tauri/` in this repository |
| Viewer, grid, SQL console, workers and database behavior | The [extension repository](https://github.com/zknpr/SQLite-Explorer), including its desktop build target |
| Copied viewer and native runtime artifacts | `viewer-dist/`, generated by `scripts/sync-viewer.mjs` |

Start with the build prerequisites and platform notes in [README.md](README.md).
The exact source pin is in `viewer-dist/manifest.json`; the current pin is on
the extension repository's `desktop-v1.8.1-port` branch.

## Changing the shell

Use the checked-in npm and Cargo lockfiles:

```sh
npm ci
node scripts/sync-viewer.mjs --verify
npm test
cargo test --locked --manifest-path src-tauri/Cargo.toml --lib
cargo clippy --locked --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
```

For changes to native database operations, run the additional live-sidecar and
runtime checks with matching native artifacts:

```sh
cargo test --locked --manifest-path src-tauri/Cargo.toml --lib -- --ignored
```

## Changing the viewer or worker

Make the change in the extension source and run its relevant tests. Generate
its desktop artifacts using the extension's build script:

```sh
cd ../SQLite-Explorer
npm ci
node scripts/build.mjs
```

During development, sync the generated working-tree files into the app:

```sh
cd ../SQLite-Explorer-App
node scripts/sync-viewer.mjs --source ../SQLite-Explorer --local
node scripts/sync-viewer.mjs --verify
```

For a reviewable update, commit the upstream source and generated desktop
artifacts, then sync by that exact commit with `--ref <source-commit>`. Include
the resulting viewer and manifest changes in the app change. Do not hand-edit
generated files. Make the upstream commit available to contributors before
publishing a dependent app revision.

The sync script selects native artifacts for the current OS and CPU. Its
`--target` option supports `aarch64-macos`, `x86_64-macos`,
`aarch64-linux-gnu`, `x86_64-linux-gnu` and `x86_64-windows`. Availability of
an artifact does not establish release QA for that target.

## Validating a change

Use a disposable database to reproduce the reported behavior. For data-changing
flows, check both the visible result and the saved database independently with
SQLite. Preserve the existing SQL console, pending-edit behavior, file-ownership
checks and explicit error reporting across native and WASM engines.

`npm run test:gui` exercises the generated viewer in headless Chromium and
requires Chrome and the `sqlite3` command. It does not replace testing the
installed app. The [macOS QA report](docs/macos-release-qa.md),
[Linux/Windows QA report](docs/linux-windows-release-qa.md) and
[native smoke checklist](scripts/qa/smoke-checklist.md) describe OS checks and
their current limits. Keep local screenshots, fixture databases and installers
under the ignored `artifacts/` directory.

Describe the user-visible problem, the change and the validation in each pull
request. Reference any corresponding extension change and distinguish tests
that passed from checks that remain unexecuted.
